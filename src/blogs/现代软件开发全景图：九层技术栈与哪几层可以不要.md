网上流传一张很有名的架构图，叫 **The Modern Software Stack**。九层，从你眼睛看到的按钮，一路排到机房里的 Kubernetes。第一眼看上去信息量很大，多数人的反应是"这么多东西，得学到哪一年"。

我把它翻来覆去看了几遍，觉得这张图最值钱的地方不是那九层。是**九层里有四层你永远躲不开，剩下五层全是长出来的**。

## 先把结论摆出来

先把它压成一句话：**删掉之后产品还能上线、还能正常服务用户的，是长出来的层；删掉就完全跑不起来的，是必需的层。**

按这个标准，九层里只有四层是任何项目都躲不开的——**L1 展示层、L5 业务逻辑层、L7 数据存储层、L9 基础设施层**。剩下的五层全是规模长出来的器官。

原图标了三层 Optional：边缘与传输、消息与异步、分析与 AI。我的看法是：**标少了。集成层（L3）和数据访问层（L6）在多数项目里同样是可选的**——它们不是不存在，而是在小规模阶段它们只是几个函数，还配不上"一层"这个称呼。

另外一个更重要的判断：**这九层是逻辑关注点，不是九个进程**。原图竖着排，看起来像九个依次排列的服务，实际一个单体应用里，L3、L5、L6 可能就躺在同一个进程的三个包目录里。把逻辑分层当成部署拓扑，是"过度微服务化"最常见的第一步。

下面逐层过一遍。每层我只回答三个问题：它管什么、图上那堆工具是不是一类东西、以及它真正难的地方在哪。

## 逐层拆解

### L1 展示层：真正的决策不是选框架，是选渲染位置

这层负责把数据变成人能操作的界面。

图上把 React、Angular、Vue.js、Tailwind CSS、Flutter、Swift、Kotlin 并排放了，但**它们不是一类东西**：前三个是浏览器里的渲染库，Flutter 自带渲染引擎（不依赖 WebView），Swift / Kotlin 是原生客户端语言，而 Tailwind 是样式方案——它和任何框架都能组合。你完全可以 Vue + Tailwind，也可以 Flutter + 自己的一套设计系统。

这层真正难的决策不在框架，在**渲染发生在哪里**：

- CSR（客户端渲染）：首屏空，SEO 弱，但交互快、部署就是几个静态文件；
- SSR / SSG：首屏和 SEO 都解决，代价是你多了一个需要运维的渲染服务（这一下就碰了 L9）；
- 原生 / 跨端：拿到系统能力和性能，代价是两套发布流程。

这个选择会**反向约束另外两层**：选 SSR，L2 的缓存策略就得考虑动态内容怎么失效；选原生，L3 就得设计一套面向多端的版本化 API。框架是三年一换的，渲染位置是五年不改的。

### L2 边缘与传输：唯一一层"加了之后错误更难查"的

职责只有一句话：让地球另一端的人少等几百毫秒。CDN 缓存静态资源、DNS 就近解析、TLS 在边缘终止、顺手做一层 WAF 挡掉扫描器。

图上是 Cloudflare、Akamai、Fastly、CloudFront——全是商业 CDN，也全是**别人的基础设施**。这点很多人没意识到：这层你几乎从来不"自建"，只"接入"。

它真正难的地方是**缓存失效策略**。缓存是整张图里最特殊的一层：加了它之后，线上问题会变得更难查。用户看到旧数据来报障，你在源站翻日志，什么都翻不到——因为请求根本没到源站。所以这层必须配一个能力：能按 URL、按版本号、按发布批次精确地"捅掉"缓存。

什么时候需要：用户地理分布跨越大洲，或者静态资源流量成为账单上的主要项。国内的业务，云厂商自带的 CDN 基本就够，不必单独把它当一层来设计。

### L3 集成层：协议的选择，本质是交互模式的选择

这层定义"外面怎么跟你说话"。

图上这四个东西的性质完全不同，值得拆开说：

- **Postman** 是调试工具，不是运行时组件，它不该出现在架构图里；
- **gRPC / GraphQL / WebSocket** 是三种协议，各自对应一种交互模式；
- **API Gateway** 是部署组件，管限流、鉴权、路由。

协议怎么选，其实是问"你的交互长什么样"：资源增删改查用 REST 最省心；客户端需求差异大、后端字段多（比如 App 首页要拼五个模块）用 GraphQL 能少跑几趟；内部服务之间高频调用用 gRPC，二进制序列化 + 强契约；服务端要主动推消息，就上 WebSocket 或 SSE。

这层真正难的是**契约演进**，不是转发请求。加字段是兼容的，改字段语义不是。一个 API 层的核心工作从来都是版本管理——v1 什么时候能下掉、老客户端还占多少比例、破坏性变更怎么灰度。这件事没有技术方案能替你解决。

### L4 消息与异步：这一层引入之后，"恰好一次"就不存在了

职责是把"必须马上做完"翻译成"稍后一定会做完"。双 11 下单不可能一秒钟处理完所有事情，排队、异步、补偿，都是这层的事。

同样，图上的工具混了两个种类：Kafka / RabbitMQ / SQS 是**消息中间件**，Celery / Sidekiq 是**任务队列的客户端库**（它们得配一个 broker 才能跑）。把它们并排会产生一个误解：以为装个 Celery 就有了消息队列。

三者的差异其实很清楚：

- **Kafka**：日志型，消息 append 后不删，可以重放、可以多个消费者各读各的。适合"事件流"——订单状态变更、用户行为埋点。
- **RabbitMQ**：路由灵活（exchange / routing key），消息消费完就没了。适合"任务分发"。
- **SQS**：托管、简单、零运维，代价是能力也最基础。

这层真正难的是三件事：**幂等、顺序、死信**。异步一旦引入，"恰好处理一次"就不存在了，你能选的只有"至少一次投递 + 消费端幂等"。所有以为"加个队列就解耦了"的项目，最后都在这三件事上补了半年。

什么时候需要：用户点了按钮要干等三秒以上，或者下游的服务挂掉不该拖垮上游。反过来说，如果你的同步调用链路一直很顺，这层就不该存在。

### L5 业务逻辑层：唯一不能外包给框架的一层

这里是灵魂。所有规则、计算、判断，都在这一层。

Spring（Java，生态最全也最重）、Laravel（PHP，约定优于配置）、Django（Python，自带 admin 和 ORM）、Express（Node，极小内核，一切靠中间件）、.NET Core（C#，性能和工具链都强）。

这五个框架的共同点是：它们**只给你脚手架**——路由、依赖注入、事务边界、请求校验。业务规则得你自己写，而且换任何框架都省不掉。这就是为什么"选框架"这件事的重要性被高估了：框架决定你的手感，业务逻辑决定你的产品。

这层的腐化是**静默的**。没有编译错误，没有告警，只有越来越长的 service 方法。三个可以量化的信号：

- 一个函数超过 50 行；
- 一个函数超过 4 个入参；
- 函数名里出现 "and"（`validateOrderAndDeductInventory`）。

出现任何一个，说明这里藏着两个以上的职责，该拆了。

### L6 数据访问层：它的真实价值是"换存储时改动边界刚好落在这里"

职责是把业务层的对象操作翻译成存储层的读写。

这层图上的四样东西又是混的：Redis 和 Elasticsearch **本身是存储**（内存 KV、倒排索引），Hibernate / Sequelize / SQLAlchemy 才是 ORM（对象关系映射）。

判断一个 ORM 到底算不算"一层"，我有个很实用的标准：

> 换存储引擎的时候，改动的边界是不是刚好落在这层？如果改动会漏到业务代码里去，那它只是语法糖，不是架构层。

按这个标准，大量项目里的 ORM 就只是语法糖——因为它一辈子只连着同一个 PostgreSQL，业务代码里也到处是 `db.query(...)`。这不丢人，反而说明抽象得刚刚好。真正的抽象成本，只有在"要换存储"或者"要加缓存/读写分离"时才会兑现收益。

### L7 数据存储层：选型只看一件事，数据之间的关系有多强

不丢数据，就这一件事，但它不可逆，所以最需要谨慎。

- **PostgreSQL**：类型系统强，JSONB 能存半结构化数据，扩展生态好（有了 JSONB 之后，很多"必须上文档库"的理由消失了）；
- **MySQL**：生态最广，会运维的人最多，遇到问题搜得到答案；
- **MongoDB**：结构灵活，代价是"灵活"会把 schema 的问题全部推到业务代码里——数据库不管的事，代码里总得有人管；
- **BigQuery / Snowflake**：列存、按扫描量计费、为分析而生，不适合高频点查。

选型判据我只认一条：**先问数据之间的关系有多强**。订单、商品、用户之间是强关系，天然需要外键和跨表事务，那就是关系型。日志、内容、配置这类弱关系数据，文档型更省事。至于"哪个性能高"，在你有真实数据量之前，这个问题没有答案。

### L8 分析与 AI：训练和推理是两条完全不同的链路

职责是从历史数据里找规律，或者做预测。

Spark（批处理）、PyTorch / TensorFlow（训练框架）、Databricks（托管平台）、Looker（BI 可视化）——注意，**这层图上的东西全部偏训练和分析侧**。

上线时你会发现缺了一大块：推理在哪跑？特征从哪来？很多团队以为"用了 PyTorch 就有 AI 能力"，实际缺的是特征管道和在线推理服务。训练是离线批量的，可以跑几小时；推理是在线实时的，得在几十毫秒内返回。两条链路的技术栈几乎不重叠。

什么时候需要：有稳定的历史数据和明确的预测目标。没有数据的时候，先上 Looker 做 BI 比先训模型有用一百倍——因为你会发现业务问题根本不需要模型，一个报表就够了。

### L9 基础设施层：Docker 无脑值得，Kubernetes 不一定

职责是让上面八层有地方跑、挂了能重启、流量大了能扩容。

AWS / Azure / GCP 是云，Docker 是打包，Kubernetes 是编排。这三件事的"必要性"完全不同层级：

- **容器化（Docker）几乎无脑值得**。它解决的是"我这能跑，你那跑不了"这个真实痛点，成本很低。
- **编排（Kubernetes）要到"多服务 + 需要弹性"才值得**。K8s 不是部署工具，它是分布式系统的操作系统——你用它的那一刻，等于承认自己有一个需要调度、服务发现、滚动升级、配置管理的集群。三台机器以下的团队上 K8s，是负收益。

这三种东西的成本形态也不一样：云和托管服务是**账单**，Docker 是**学习成本**，K8s 是**常驻的运维人力**。判断标准不是"大厂都这么做"，而是"这笔成本记在谁头上"。

左边九个框是**代码里的关注点**，右边三个框是**运行时的位置**。这张对照图能纠正两个常见误解：

**误解一：九层 = 九个服务。** 不是。L3 / L5 / L6 在单体里就是同一个进程的三个包目录。拆不拆，取决于有多少个团队要并行改这块代码（康威定律），不取决于架构图上有几个框。

**误解二：分层图上的箭头表示"可以调用"。** 也不对。分层图的真实规范是**禁止跨层调用**——展示层不能绕过业务层直接写 SQL。这个错误在教程代码里特别常见：

```js
// ❌ 控制器跨过业务层，直接摸数据库
app.get('/orders/:id', async (req, res) => {
  const { rows } = await db.query('SELECT * FROM orders WHERE id = $1', [req.params.id])
  res.json(rows[0])
})
```

这行代码能跑，测试也过。但它意味着：加缓存要改控制器、换表结构要改控制器、加权限校验还是要改控制器。一层的边界被戳穿，后面所有变更都会从那个洞漏进来。

## 加层之前，先看这三个信号

"什么时候该加一层"是这张图不会回答的问题，也是团队里争论最多的。我把它压成三个可观测的信号——**能观测**很重要，意思是它不该是"我觉得将来会需要"：

**① 部署耦合。** 两个团队改同一份代码要互相等发布窗口，一个改动要全量回归。这时候该拆的是**模块边界**（先做 L3 的接口切分），而不是先拆数据库。顺序反了，你会得到两个共享一张表的"微服务"，比单体更难维护。

**② 同步链路的尾延迟。** P99 抖动，追下去发现是某个下游拖住了主流程。这时候加 L4 削峰：先把"可以稍后做"的部分挪出去，再做异步化。注意顺序——**先想清楚哪些事可以晚点做，再选 Kafka 还是 SQS**，而不是先选中间件再找场景。

**③ 读写比例失衡。** 同一份数据读的 QPS 远高于写，且业务能容忍秒级不一致。这时候加缓存，而且**缓存要加在 L6，不要加在 L5**。写在业务逻辑里的 `redis.get()` 会让缓存策略散落在几十个函数里，永远理不清失效规则。

三个信号都没有的时候，加层就是在给未来的自己加运维负担。这也是我对这张图最大的不满：它列了工具，没列**代价**。每多一层，就多一份要监控的指标、一个要值班的组件、一个升级时要回归的边界。九层全齐的架构，一个"下单失败"的排查路径要穿过日志聚合、链路追踪、消息死信、缓存一致性和网关限流五个系统。

## 工具之外，还有一件图没画的事

原图在「边缘与传输」「消息与异步」「分析与 AI」三条后面都标了 Optional。标注是对的，但这三个"可选"背后其实是三件完全不同的事：

- **L2 可省**，因为它是天然的外挂——你几乎从不自建，只接入，成本是一笔账单；
- **L4 可省**，因为低并发时同步调用能完全替代它，代价只是慢一点；
- **L8 可省**，因为它在没有历史数据时无事可做，不是"暂时不需要"，是"无事可做"。

三种"可选"背后是三条不同的理由。这说明一句更普适的话：**每一层存在的理由，都是某一类物理约束**——地理距离（L2）、处理时延（L4）、数据规模（L8）、计算资源（L9）、并发一致性（L7）。约束不出现，层就不该出现。而约束一旦出现，你躲不掉，只能选择自己扛还是花钱买。

所以"要不要这层"这个问题，真正的形式是：**这个约束现在存在吗？我愿意为它付多少钱？**

## 我可能错在哪

上面整套"能省就省"的判断，在两种情况下会失效，我先把它们说出来：

**一是有刚性合规或审计要求的时候。** 金融、医疗、政企项目里，网关的审计日志、数据的可追溯、离线分析的留存，都不是"业务需要"而是"监管需要"。这些层不能等规模长出来，必须开工就建——此时按需加层的思路是错的。

**二是多团队协作的产品。** 我上面说"拆服务取决于团队规模"，但反过来也成立：如果一开始就有五个团队要并行开发，边界成本远低于沟通成本，那**提前把层划清楚是对的**。康威定律是双向的——系统结构会反映组织沟通结构，与其让它自发长歪，不如先划好。

换句话说，这张图的正确用法不是"照着搭"，也不是"尽量少搭"，而是**先确认你被哪些约束绑住了**。被绑住的那几层，认真建；没被绑住的，留个接口位置就够了。

一个 App 从来不是"写点代码"就能上线，但也不是九层都得自己造。**优秀的团队不是把九层全填满，而是清楚自己为什么空着其中五层**——而且这个理由在半年后依然站得住。
