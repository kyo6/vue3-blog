Codex App 可以理解成一个**面向 AI 编程的任务工作台**：它既不是传统 IDE，也不是单纯的聊天窗口，而是把多任务、项目管理、沙盒权限、Git、云端运行、插件、Skills、MCP 和自动化集中到一个界面里。如果你已经在用 Codex CLI、Claude Code、Cursor 或其他 coding agent，Codex App 最值得关注的地方，是它把「多个 agent 并行干活」做成了一个更清晰的桌面工作流。

> 本文整合自 knightli 的《Codex App 保姆级上手》《Codex Hook 进阶玩法》以及 OpenAI 官方 Projects 文档（见文末参考链接），并结合实际落地经验做了梳理。

---

## 一、Codex App 适合做什么

Codex App 的核心价值不是让 AI 回答问题，而是让 AI 在项目目录里**持续执行任务**：

- 修改代码、运行命令、启动开发服务；
- 管理多个项目和多个任务；
- 在本地或云端执行长任务；
- 调用插件、Skills 和 MCP 扩展能力；
- 通过 Git、worktree 和 PR 管理改动。

OpenAI 官方把它定位成一个「管理多个 coding agent 的界面」。它尤其适合前端页面、脚本工具、小型应用、文档整理和自动化工作流。

---

## 二、安装与前置准备

使用 Codex App 前，建议先准备好三个基础工具：

1. `Git`
2. `Node.js`
3. `VS Code` 或你常用的 IDE

Codex App 支持 macOS 和 Windows。安装后使用 ChatGPT 账号登录，首次进入时可选择主要使用场景（编程 / 日常工作），Codex 会根据选择预装一部分插件和 Skills，后续也能在设置和插件市场里调整。

---

## 三、界面结构：项目、任务和对话

Codex App 是典型的三栏布局：

- **左侧**：项目、任务、历史对话、插件和自动化入口；
- **中间**：当前对话窗口；
- **右侧**：文件、浏览器、终端、运行结果等多功能区域。

一个项目通常对应一个本地文件夹。你可以在同一个项目里开多个对话，也可以同时打开多个项目，让不同 agent **并行执行任务**。任务列表会显示不同状态：

- **正在运行**：agent 仍在执行；
- **等待批准**：需要你确认权限、联网、安装依赖或执行高风险操作；
- **已完成**：任务结束，可查看结果或继续追问。

这比在多个终端窗口里来回切换更直观，也更适合同时管理多个 AI 任务。

---

## 四、沙盒与权限控制

Codex App 的权限体系围绕**沙盒**展开。默认情况下，当前项目文件夹会成为 agent 的主要工作范围。常见权限边界：

- 可以读取和修改项目目录内的文件；
- 默认不能随意修改项目外文件；
- 默认会限制联网或高风险命令；
- 需要越权时，会向用户申请批准。

比较实用的模式是「**自动审查**」：低风险操作由系统自动放行，高风险操作再交给用户确认。这样既能减少频繁弹窗，又能避免 agent 在不知情的情况下执行危险操作。

「**完全访问**」要谨慎开启。它适合你明确知道 agent 要做什么，且项目已有 Git 备份、重要文件也有额外备份的场景。日常使用不建议长期保持完全访问。

## 五、上下文、模型和额度

Codex App 会显示当前对话的上下文使用情况。对话越长、历史越多，模型需要处理的上下文也越大。实用建议：

- 一个任务完成后，优先开新对话；
- 长对话可手动压缩，但别把压缩当成万能记忆；
- 复杂任务先写清楚目标、边界和验收标准；
- 不要把大量无关日志、报错和文件一次性塞进对话。

模型选择上，可根据任务复杂度调整思考强度：简单修改、文案整理、重复任务不一定需要最强模型；架构迁移、疑难 bug、跨文件重构则更适合使用更强模型。如果界面里有「快速模式」，它通常会带来更高额度消耗，赶时间时可开，日常不必默认开启。

---

## 六、图片生成与多模态输入

Codex App 可以接收图片和文件作为上下文，也能在合适场景调用图像生成。对前端和内容类项目很有用：

- 根据截图修正页面样式；
- 替换网页中不合适的配图；
- 生成产品图、轮播图或页面素材；
- 根据 UI 截图指出需要修改的位置。

更高效的用法是：**不要只说「改好看一点」，而是结合截图指出具体问题**，例如「这个卡片间距太大」「这里的图和服务场景不匹配」「把地图区域做得更清楚」。

## 七、Steer：任务执行中及时纠偏

`Steer` 可以理解成「执行中接管方向」。当 agent 已开始执行，你却发现它理解错了方向，不应该等它全部跑完再改——这时可插入新的指令，让 Codex 及时修正路线。

适合使用 Steer 的场景：

- agent 误解了需求；
- 生成的页面风格明显不对；
- 正在执行的方案成本太高；
- 你临时补充了关键约束。

一般建议保留默认排队行为，只在确实需要干预时手动使用 Steer，既不打乱正常任务，也能在关键时刻把方向拉回来。

## 八、计划模式和内置浏览器

复杂任务建议先开**计划模式**：Codex 不会马上改代码，而是先输出方案，必要时还会用卡片形式追问关键选择。适合开计划模式的任务：

- 框架迁移（如从普通 React 项目迁到 Next.js）；
- 大范围重构；
- 涉及数据库、认证、部署的功能；
- 你还没想清楚技术路线的需求。

Codex App 右侧区域可打开**内置浏览器**预览本地开发服务。你可以在页面上做批注，让 Codex 按具体 UI 位置修改问题——这种「看页面、点位置、让 AI 改」的流程，比纯文字描述更适合前端调试。

---

## 九、Git、IDE 和代码回滚

Codex App 不是完整 IDE，它可以查看、批注代码，但真正的手写编辑仍更适合交给 VS Code、Cursor、Windsurf 等 IDE。建议每个 Codex 项目都尽早初始化 Git：

1. 让 Codex 创建或检查 `.gitignore`；
2. 在完成一个可用状态后提交一次；
3. 每次大改前确保有干净提交点；
4. 不满意时用 Git 回滚代码。

注意：**只回滚对话历史，代码不会自动跟着回滚**。比较稳的做法是——对话层面回到合适节点，代码层面用 Git commit hash 回到对应状态。

## 十、Worktree：并行开发多个方向

`git worktree` 是 Codex App 里非常适合并行 agent 的能力。本质是：基于同一仓库创建多个独立工作目录，每个目录对应不同分支，让不同 agent 在不同文件夹里同时开发，互不覆盖。

典型用法：

- 一个 worktree 优化客户评价组件；
- 一个 worktree 调整门店信息和地图布局；
- 两个任务完成后分别合并回主干；
- 合并完成后删除临时 worktree。

这比在同一目录里让多个 agent 同时改代码稳得多。遇到冲突时，也可按正常 Git 流程 review 和合并。

## 十一、云端运行环境

Codex 不只能在本机工作，也能把任务委托到**云端环境**执行。适合这些场景：

- 出门在外，手边只有手机；
- 希望 agent 在后台跑长任务；
- 代码已同步到 GitHub，需要让 Codex 基于远端仓库修改；
- 希望通过 PR 形式审查和合并改动。

典型流程：先把本地代码推到 GitHub，再让 Codex 在云端环境中拉取仓库、执行任务、生成改动，最后以 PR 或 diff 的方式交给你审核。本地继续开发时，要记得把远端最新改动同步回来。

---

## 十二、记忆系统：写好 AGENTS.md

新对话默认没有完整历史记忆。项目一复杂，如果每次都重新解释背景会很浪费。最通用的做法是在项目根目录维护 `AGENTS.md`，记录：

- 项目目标和主要技术栈；
- 常用命令；
- 目录结构说明；
- 代码风格和命名约定；
- 禁止事项（例如不要批量删除文件）；
- 测试、构建和部署规则。

你也可以让 Codex 先通读项目，再生成一版 `AGENTS.md`，然后人工审一遍。复杂项目里这个文件非常值得维护。

全局规则要谨慎：适合写所有项目通用的安全约束（如「不要递归删除目录」「执行破坏性操作前必须确认」）。不要把某个项目的细节写进全局规则，否则会污染其他项目。

---

## 十三、插件和自动化

**插件**用于把外部服务接入 Codex，例如 GitHub、Gmail、Google Drive、数据库、部署平台。价值在于减少复制粘贴——你可以让 Codex 查看某仓库的 star 趋势、整理邮件、定期执行检查任务、把结果写成摘要。

**自动化**适合重复任务，例如每周五下午检查一次仓库数据并发送邮件报告。简单自动化任务通常不需要最强模型，选择较轻量的模型即可。

---

## 十四、Skills：把工作流变成可复用能力

**Skills 是 Codex 的「专业说明书」**——它不是单次提示词，而是把某类任务的流程、规范、脚本和注意事项沉淀下来，让 Codex 后续稳定复用。常见来源：

- 官方 Skills；
- 第三方 Skills；
- 自己编写的 Skills。

适合做成 Skill 的工作：

- 把字幕整理成图文笔记；
- 按公司规范写周报；
- 批量处理图片或文档；
- 固定格式的代码审查；
- 特定框架的项目初始化。

如果某个提示词你已经复制粘贴了很多次，就值得考虑把它做成 Skill。

---

## 十五、MCP：接入外部工具和数据库

**MCP** 是给大模型使用的标准化工具协议。通过 MCP，Codex 可以调用外部服务完成更具体的任务。例如接入 Supabase 后，可以让 Codex：

- 创建数据表；
- 读取数据库结构；
- 修改后端接口；
- 把前端表单提交到数据库；
- 根据数据库状态调试问题。

这类能力很强，但要注意权限边界：数据库、生产环境、部署平台、邮件账号都属于高风险资源。第一次接入时，最好使用**测试项目和低权限账号**。

---

## 十六、部署插件

部署平台插件可让 Codex 直接完成构建和发布，例如把前端项目部署到 Netlify 一类平台。它适合小型网站、原型页面、内部工具和展示项目。实际使用时注意：

- 部署前先跑本地构建；
- 环境变量不要直接写进代码；
- 发布后检查页面能否正常访问；
- 生产项目要保留人工 review。

AI 可以帮你打通发布流程，但发布权限仍要谨慎管理。

---

## 十七、电脑自动化（RPA）

在支持的平台和插件环境里，Codex 还可以操作浏览器或桌面应用，完成更接近 RPA 的任务：

- 打开聊天软件并准备一条消息；
- 浏览项目看板，汇总任务状态；
- 生成英文简报，在你确认后发送给指定对象；
- 把这套流程做成定时自动化。

这类功能很有想象力，但也最需要安全边界。凡是涉及**发消息、发邮件、提交表单、付款、删除数据**的操作，都应保留人工确认。

## 十八、用 Projects 组织相关工作

根据 OpenAI 官方文档，Codex 的 **Projects** 视图把「ChatGPT 项目」和「本地项目」合在一起管理。它的核心作用是给 ChatGPT 提供共享上下文，并组织相关工作。

### 18.1 什么时候用项目

- **创建项目**：工作会持续一段时间、产生多个产出、或依赖相同的文件和来源时；
- **不开项目**：工作是自包含的、不需要共享项目上下文时，直接用 `New chat` 即可。

### 18.2 本地项目与文件夹 / 代码库

添加**本地项目**时，ChatGPT 需要读取或修改你电脑上的文件。项目不一定需要文件夹，但可按需附加文件夹：

- 打开项目菜单 → **Edit project** → **Add folder** 可附加多个文件夹；
- ChatGPT 可读写每个附加文件夹里的文件；
- 指向某个文件夹并 **Make primary** 可设为默认工作目录，新对话从这里开始；
- **Codex 也会用这个主文件夹作为 Git 操作、`AGENTS.md`、Skills、`config.toml` 的默认发现目录**；
- 次要文件夹仍可用于文件搜索、读取和编辑，但 Codex 不会自动从次要文件夹发现这些项目文件；
- 相关工作分散在不同位置时（如 app 与其文档、网站与其后端），可用多个文件夹；不相关的工作或每个对话只应访问仓库一部分时，应创建独立项目。

### 18.3 组织与归档

- **Pin a project / chat**：钉在侧栏顶部，方便常回看（钉住不改变 Codex 能访问的内容，只改变显示位置）；
- **Rename a chat**：用简短结果名，如「Q3 发布简报」「结算页无障碍审查」；
- **Search**：在 Projects 视图按 `Cmd/Ctrl + G` 搜索历史对话；
- **Archive a chat**：完成后归档，从 Projects 设置里可恢复（`Settings > Archived chats`）。

### 18.4 与沙盒、worktree 的关系

- Projects 和 worktree 都用于组织工作，但真正约束本地命令能读什么、改什么、能否联网的是 **沙盒（sandbox）**；
- 在某个 worktree 里开对话时，其他文件夹仍保持附加；
- 远程项目目前只支持一个文件夹。

## 十九、进阶玩法：用 Hook 把规则接进执行循环

很多人用 Codex 时，重点都放在「让它帮我写代码、改文件、跑命令」。但如果只停留在这里，很容易忽略一个更适合进阶的功能：**Hook**。

Hook 的价值不在于让 Codex 更会写代码，而在于让它更**按规矩工作**。它可以在 Codex 的关键生命周期事件里运行自定义脚本（例如用户提交提示词时、工具调用前、工具调用后、请求权限时、会话停止时），从而把团队规则、安全检查、隐私保护和自动化记录放进工作流，而不是每次都靠人工提醒。

一个典型例子是**隐私检查**：用户把 prompt 发给 Codex 前，先用 Hook 扫一遍是否包含 API key、token、私钥、手机号、内部地址等敏感信息。命中规则就阻止提交，或给出明确提示让用户先清理。

### 19.1 Hook 放在哪里

Codex 可从 `hooks.json` 加载 Hook，也可从 `config.toml` 里的 `[hooks]` 表加载内联配置。常用位置：

- `~/.codex/hooks.json`（用户级）
- `~/.codex/config.toml`（用户级）
- `<repo>/.codex/hooks.json`（项目级）
- `<repo>/.codex/config.toml`（项目级）

用户级 Hook 适合个人通用规则（「不要把疑似密钥发出去」「每次结束做摘要」）；项目级 Hook 适合仓库规范（「禁止直接改生成目录」「提交前检查 front matter」）。

⚠️ **项目级 `.codex/` 配置只有在该项目层被信任后才会加载；用户级 Hook 不依赖项目是否被信任。** 这个设计很重要——项目里的 Hook 本质是会执行本地脚本的配置，不能对陌生仓库无条件信任。

### 19.2 常见触发时机

不同事件适合不同用途：

| 事件 | 触发点 | 适合做什么 |
|------|--------|-----------|
| `UserPromptSubmit` | 用户 prompt 即将提交 | 隐私检查、敏感词检查、提示词规范检查 |
| `PreToolUse` | Codex 调用工具前 | 拦截命令、文件写入、MCP 工具调用 |
| `PermissionRequest` | Codex 准备请求权限时 | 自动批准 / 拒绝某些明确请求 |
| `PostToolUse` | 工具执行后 | 检查输出、扫描生成文件、提醒后续步骤 |
| `SessionStart` | 会话开始 / 恢复 | 加载项目约定、团队规范、本地提示 |
| `Stop` | 一轮响应准备停止时 | 收尾检查（测试、TODO、补验证） |

其中 `PreToolUse` 可以拦截很多工具调用，但官方明确提示它**还不能完全覆盖所有 shell 调用路径、也不能拦截所有非 shell / 非 MCP 工具**——真正高风险场景仍需权限配置、沙箱、代码审查和最小权限配合。

### 19.3 一个隐私检查 Hook 怎么设计

隐私检查最适合放在 `UserPromptSubmit`，因为它发生在用户内容真正进入 Codex 工作流之前。先覆盖最容易误贴的内容就够：

- OpenAI、GitHub、云厂商等 API key；
- `-----BEGIN PRIVATE KEY-----` 这类私钥块；
- `.env` 文件片段；
- 访问令牌、Bearer token、JWT；
- 内网域名、数据库连接串；
- 身份证、手机号、邮箱等个人信息。

Hook 脚本从标准输入读取 JSON，取其中的 `prompt` 字段，用正则或规则表扫描。发现问题可返回阻止结果：

```json
{
  "decision": "block",
  "reason": "检测到疑似 API key，请先移除敏感信息后再提交。"
}
```

对于密钥、私钥和令牌这类高风险内容，更稳妥的做法是**直接阻止**，而非只返回上下文提示。

### 19.4 hooks.json 配置示例

仓库级配置，创建 `.codex/hooks.json`：

```json
{
  "hooks": {
    "UserPromptSubmit": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python .codex/hooks/privacy_check.py",
            "timeout": 10,
            "statusMessage": "Checking prompt privacy"
          }
        ]
      }
    ]
  }
}
```

对应脚本从标准输入读取 JSON：

```python
import json
import re
import sys

payload = json.load(sys.stdin)
prompt = payload.get("prompt", "")

patterns = [
    r"sk-[A-Za-z0-9_-]{20,}",
    r"ghp_[A-Za-z0-9_]{20,}",
    r"-----BEGIN [A-Z ]*PRIVATE KEY-----",
    r"Bearer\s+[A-Za-z0-9._-]{20,}",
]

for pattern in patterns:
    if re.search(pattern, prompt):
        print(json.dumps({
            "decision": "block",
            "reason": "检测到疑似密钥、令牌或私钥，请先移除敏感信息。"
        }, ensure_ascii=False))
        raise SystemExit(0)
```

这个示例只演示思路，实际应把规则拆成可维护的列表并控制误报：规则越严格越容易误拦（普通文档里出现 `Bearer` 示例不一定就是泄露，项目里也可能有用于测试的假 key）；规则越宽松越容易漏掉真实风险。

### 19.5 config.toml 内联写法

不想单独维护 `hooks.json`，也可写在 `config.toml` 里。内联 TOML Hook 与 `hooks.json` 使用同样的事件结构：

```toml
[[hooks.PreToolUse]]
matcher = "^Bash$"

[[hooks.PreToolUse.hooks]]
type = "command"
command = 'python ".codex/hooks/pre_tool_use_policy.py"'
timeout = 30
statusMessage = "Checking Bash command"
```

⚠️ 若同一层配置里同时存在 `hooks.json` 和内联 `[hooks]`，Codex 会同时加载并给出警告。实际项目里最好二选一，避免规则分散后难以排查。

### 19.6 使用 Hook 时要注意什么

1. **审查来源**：Hook 会执行本地命令，非托管 Hook 需被 review 和 trust 后才运行；内容变化后也要重新信任，陌生仓库里的 `.codex/hooks.json` 不要随便放行；
2. **多个匹配的 Hook 可能都运行**：明确哪些是用户级、哪些是项目级、哪些是管理员托管规则，避免互相冲突；
3. **Hook 是护栏，不是完整安全边界**：高风险的场景仍需权限配置、沙箱、代码审查和最小权限配合；
4. **Hook 脚本要快**：隐私扫描、命令审查发生在交互链路中，脚本每次跑几十秒会直接拖慢体验；
5. **输出格式要严格**：不同事件支持的返回字段不完全一样（如 `UserPromptSubmit` 用 `decision: "block"` 阻止，`PreToolUse` 有独立的 `hookSpecificOutput` 结构），写前先看对应事件的输入输出约定。

### 19.7 最值得先做的三个 Hook 场景

- **隐私检查**：最容易带来真实收益，适合个人和团队通用；
- **危险命令拦截**：针对 `Bash` 的 `PreToolUse` 做基础规则，阻止递归删除、改写系统目录、向未知远端上传文件；
- **收尾检查**：用 `Stop` 或 `PostToolUse` 提醒 Codex 在结束前确认测试、构建、格式化、文档和未提交改动（不一定要强制阻断，但能减少「差一步就收工」）。

## 二十、使用建议

Codex App 的正确打开方式，不是让它一次性全自动接管一切，而是把任务拆清楚，让它在受控环境里高效执行：

- 每个项目先初始化 Git；
- 复杂任务先开计划模式；
- 并行任务优先用 worktree；
- 项目规则写进 `AGENTS.md`；
- 高风险操作保留人工确认；
- 重复流程沉淀成 Skill 或自动化；
- 插件和 MCP 先在测试环境验证；
- 用 Hook 把隐私、安全和流程要求变成每次都会自动触发的默认动作。

真正用好它的关键，是在「放权」和「控制」之间找到平衡。小任务大胆交给 Codex，复杂任务先让它计划，高风险动作必须确认——这样它才会从一个会写代码的助手，变成可以长期协作的工程工具。
