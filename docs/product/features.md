# PPT Outline

## Overview

本 PPT 解读 Slack Engineering 提出的 Agentic Testing（智能体驱动测试）：在快速迭代的系统中，传统端到端测试所依赖的"固定步骤、稳定选择器、可预测流程"三个假设不断失效，维护成本随之上升。Slack 的做法是把 E2E 层的一部分责任从静态脚本交给按高层意图执行的 AI 智能体——测试被表达为目标而非步骤序列，智能体在每一步评估应用状态并动态选择动作，遇到 UI 结构改动或元素迁移时尝试替代路径而非立即失败，最终仍与工程师定义的断言比对。

全篇 17 页，三段式结构：先讲清传统 E2E 为何失守，再讲智能体测试的执行机制与可观测性设计，最后明确它的边界、护栏与落地路径。核心结论是——智能体测试是 E2E 层的**补充能力**而非替代品：确定性测试继续承担 CI 中的高频回归验证，智能体执行用于处理高变更、高脆弱场景的探索与调试；受成本考量，它目前更适合定向调试与探索性测试，不适合在 CI 中高频执行。

### Page 4: 三个隐含假设正在失效
- **Page Type**: Content
- **Page Title**: 三个隐含假设，撑不住快速迭代
- **Content Structure**:
  - 固定步骤：脚本假定操作顺序恒定不变，任何一步插入或重排都会让后续全部错位。
  - 稳定选择器：脚本依赖 DOM 结构、class 与 id 不变，而 UI 重构几乎必然触碰它们。
  - 可预测流程：脚本提前枚举 UI 与 API 的行为路径，一旦分支变化即失去覆盖。
  - 结果：三个假设同时松动，维护投入随迭代频率持续上升。

### Page 5: 脆断的代价
- **Page Type**: Content
- **Page Title**: 脆断的代价：假失败淹没真回归
- **Content Structure**:
  - 表面变更被判失败：UI 结构改动、元素位置迁移，都会被确定性脚本读成测试失败。
  - 维护成本持续累积：每一次界面调整都要人工修复选择器与步骤，力气花在脚本而非产品上。
  - 信号被噪声淹没：红灯太多之后，团队会默认忽略失败，真正的回归反而被漏掉。
  - 三个数字：3 类表面变更 / 1 个最敏感层（E2E）/ 0 真实功能回归

### Page 6: 章节过渡 02
- **Page Type**: Transition
- **Page Title**: 02 从脚本到意图
- **Page Subtitle**: 把责任从静态脚本，交给按目标执行的智能体

### Page 7: 核心转变
- **Page Type**: Content
- **Page Title**: 测试从"一段步骤"变成"一个目标"
- **Content Structure**:
  - 传统：click → click → type → assert；固定序列，改动即失败。
  - 智能体：goal → agent adapts → verify result；目标导向，按观察状态动态选路。
  - 关键差异：测试被表达为 objective 而非严格序列，由智能体解释意图并尝试完成工作流。
  - 结论：断言仍由工程师定义，智能体只负责"如何到达"。

### Page 8: 执行循环
- **Page Type**: Content
- **Page Title**: 智能体执行循环：六步闭环
- **Content Structure**:
  - 接收意图：测试意图被传入智能体层。
  - 规划：智能体做 planning，把目标拆成可执行的动作计划。
  - 执行：对被测系统的 UI 或 API 表面执行动作。
  - 观察：读取并评估当前应用状态。
  - 迭代：重复执行—观察，直到目标完成或触发停止条件。
  - 校验：执行结果与工程师预定义的断言比对。

### Page 9: 自适应能力
- **Page Type**: Content
- **Page Title**: 遇到变更：不立即失败，先换路再走
- **Content Structure**:
  - 遭遇变更：UI 结构被修改、元素被迁移到别处。
  - 重新评估：智能体在每一步评估应用状态，据此重新决策。
  - 选择替代路径：尝试 alternate paths 继续执行，而不是立刻判定失败。
  - 收敛：目标达成或触发停止条件后结束，结果仍交给断言校验。

### Page 10: 可观测性
- **Page Type**: Content
- **Page Title**: 没有执行轨迹，就没有归因
- **Content Structure**:
  - 阶段一 意图输入：测试目标进入智能体层，成为本次运行的起点。
  - 阶段二 执行记录：结构化日志记录每一步的决策与交互，形成 execution traces。
  - 阶段三 回放检视：团队可以 replay 整条轨迹，把失败定位到具体步骤。
  - 要点：动作序列可追溯 / 决策依据可解释 / 失败可复现 / 结果可审计

- **Page Subtitle**: 它该做什么，更重要的是——它不该做什么

### Page 12: 分工对比
- **Page Type**: Content
- **Page Title**: 确定性测试与智能体测试：分工，而非替代
- **Content Structure**:
  - 确定性 E2E：在 CI 中做快速、可重复的回归验证，是校验核心逻辑与契约正确性的主要机制。
  - 智能体执行：以目标为导向，观察应用状态后动态决定如何达成，用于吸收 UI 与结构变化带来的脆弱性。
  - 确定性测试 = "是否发生回归"的判据。
  - 智能体测试 = 减少表面变更造成的误报。

### Page 13: 测试金字塔第四层
- **Page Type**: Content
- **Page Title**: 测试金字塔，多出第四层
- **Content Structure**:
  - 四层金字塔（自下而上）：单元测试、集成测试、E2E 测试、智能体测试。
  - 单元测试：数量最多、执行最快的基础校验。
  - 集成测试：验证模块间协作与契约。
  - E2E 测试：覆盖完整用户旅程，对 UI 与结构变化最敏感。
  - 智能体测试：置于 E2E 层内，负责高变更、高脆弱场景的探索与调试。

### Page 14: 成本边界
- **Page Type**: Content
- **Page Title**: 成本，决定了它的边界
- **Content Structure**:
  - 更适合：定向调试、探索性测试、复杂 UI 行为探索、复现生产问题。
  - 暂不适合：在 CI 流水线中高频执行——Slack 工程师明确将成本列为主要考量。
  - 判断标准：一次运行能省下的排查时间，是否高于一次智能体执行的成本。
  - 数据卡：2 类推荐场景 / 1 条成本硬约束 / 0 —— 对确定性测试的替换次数

### Page 15: 护栏与约束
- **Page Type**: Content
- **Page Title**: 治理：先装护栏，再放它跑
- **Content Structure**:
  - 允许的动作范围：限定智能体可以执行哪些操作，越界即拒绝。
  - 探索边界：限定它在应用中的探索范围，避免偏离测试目标。
  - 停止条件：明确什么情况下终止执行，防止无限迭代与成本失控。
  - 兜底：无论如何执行，最终仍要与工程师定义的断言比对。

### Page 16: 落地建议
- **Page Type**: Content
- **Page Title**: 落地路径：先试点，后放量
- **Content Structure**:
  - ① 选点：挑 E2E 层中变更最频繁、失败最脆的场景做试点。
  - ② 保主干：确定性测试继续承担 CI 中的高频回归，不动主干。
  - ③ 建能力：补齐意图表达、护栏配置、轨迹回放三件套。
  - ④ 换指标：用假失败率与归因耗时衡量收益，而不是用例数量。

## Design Style

- **风格**：Tech（科技风），浅色底 + 深色封面/结束页，几何线条装饰，无真实配图。
- **主色**：#266ED9（蓝）——用于标题重点、编号块、关键强调、流程图主节点。
- **强调色**：#ec95e3（粉）——用于次要强调、对照组的右侧分支、角标与数据高亮。
- **中性色**：#64748B（灰）——正文、边框、分隔线、次要信息。
- **背景**：纯白 #FFFFFF，卡片使用浅灰 #F8FAFC / #F1F5F9 做层次。
- **字体**：标题 Poppins + Noto Sans SC，正文 Inter + Noto Sans SC。
- **图示**：金字塔、流程箭头、时间轴、执行循环全部用 div / border / 圆点绘制，可编辑、可缩放、无外链与版权风险。
- **动画**：不加花哨动画，仅保留模板自带的静态装饰。
